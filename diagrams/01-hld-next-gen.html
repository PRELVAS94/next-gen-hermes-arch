Next-Gen Hermes Architecture — Local-First, Postgres-Backed

Orchestrator + six specialised agents · memory as a relational store, not markdown files
Two machines: a Mac mini M4 control plane at ~10 W · an RTX 5090 inference host, wake-on-demand
MCP tool plane · webhook event plane · zero marginal cost per token
Control / routing — intent to agents Tool plane — MCP calls out Memory plane — reads & writes Inference — LAN, mTLS

The three claims

1. Relational memory beats flat files. Facts are rows with validity windows and provenance, so memory is queried — current truth is one predicate away, and contradictions between two stored beliefs become detectable instead of invisible. Corrections supersede rather than overwrite.

2. Split the silicon by bandwidth. Token generation is memory-bandwidth-bound, not compute-bound — so the heavy model takes the GPU's 1,792 GB/s, and always-on orchestration sits on Apple silicon at ~10 W. The control plane costs about €18/year to run; the 575 W GPU host sleeps until a task needs real reasoning.

3. MCP + webhooks make it a system. MCP standardises tools; webhooks invert "agent polls" into "event wakes agent" — and here the wake-up can power on the inference host too. In the deployed fleet, 172 of 314 weekly runs produced no output at all.

Honest trade-offs

Two machines mean a network is now in the path — mTLS on the LAN, health-probed, degrading explicitly rather than silently if the inference host is unavailable. A 575 W card is a real power draw, so wake-on-demand is a requirement rather than a nicety. Local models still trail frontier models on the hardest reasoning, so a burst escape hatch stays in the design. And a relational store makes retrieval precise; it does not make what you stored correct.
